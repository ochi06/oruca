# ハプティクス（触覚フィードバック）導入の検討たたき台（Issue #38）

**位置づけ**：2026-08-16時点で未決定・後回しとされていたIssue #38の調査結果。
`expo-haptics`は既に依存パッケージとして導入済みで、Issue #169（入室通知の
振動設定）で部分的に使われている。本ドキュメントは、それを他の操作（ボタン
タップ等）にも広げるかどうかの判断材料をまとめたたたき台で、実装はしていない。

## 1. 現状

- `expo-haptics`は`app/package.json`に既に存在する（新規パッケージ追加は不要）
- 唯一の既存利用箇所は`app/hooks/usePushNotificationRegistration.ts`：フォア
  グラウンドで入室通知を受信した瞬間、`USERS.entry_vibration_enabled`
  （設定画面でON/OFF可能）を見て`Haptics.notificationAsync(Success)`を呼ぶ
  （Issue #169）
- ボタン押下・スイッチ切替など、それ以外のUI操作では一切使われていない
- 共有コンポーネント`app/components/Button.tsx`・`app/components/IconButton.tsx`
  は、アプリ内のほぼ全てのタップ操作がここを通る構造になっている
  （個別画面でPressableを直書きしている箇所は現状見当たらない）

## 2. プラットフォーム対応状況

- iOS/Android：Taptic Engine / Vibratorを使ったネイティブ実装
- **Web（Issue #190簡易体験版）**：SDK 57時点の`expo-haptics`は、Web向けに
  `navigator.vibrate()`（対応端末）または非対応環境（iOS Safari等）向けの
  フォールバック（非表示の`<input type="checkbox" switch>`をクリックして
  OS側のスイッチ用ハプティクスを間借りする実装）を内蔵しており、呼び出し側
  でのプラットフォーム分岐は不要（`node_modules/expo-haptics/src/
  ExpoHaptics.web.ts`で確認）
- → 新規パッケージ・Web分岐コードを増やさずに、既存の呼び出し方のまま全
  プラットフォームに展開できる見込み

## 3. 導入するとした場合の候補ポイント

| 操作 | 候補API | 備考 |
|---|---|---|
| 通常のボタンタップ（`Button`/`IconButton`共通化） | `impactAsync(Light)` | 最も汎用的。共通コンポーネントに1箇所足すだけで全画面に効く |
| スイッチ切替（匿名モード・入室通知振動のON/OFF等） | `selectionAsync()` | `Switch`はPressableを使わないラッパーなので、`Button`側の共通化だけではカバーできない。各画面の`onValueChange`に個別追加が必要 |
| 操作の成功/失敗（OTP確認成功、エラー表示等） | `notificationAsync(Success / Error)` | 既存の入室通知（Issue #169）と同じ系統。ログイン成功・エラートースト表示等に広げる案 |
| エリア境界越え（在室/退室の検知） | （対象外を推奨） | 頻度が読めず、位置判定の精度次第では意図せず連打される恐れがある。現状は入室通知のpush受信時のみに限定されており、ここを広げるかは別途要検討 |

## 4. 実装方式のトレードオフ

- **A. `Button`/`IconButton`に一律で組み込む**
  - 長所：1箇所の変更で全画面に波及、呼び出し側の書き換えが要らない
  - 短所：「タップ全部に鳴らす」という仕様をその場で決め打ちすることになる。
    後から「この画面だけ鳴らしたくない」という例外が出た場合、
    `Button`側にオプトアウトのpropsを追加する手間が発生する
- **B. 呼び出し側（各画面）で個別に`Haptics.xxxAsync()`を呼ぶ**
  - 長所：鳴らす/鳴らさないを画面・操作単位で選べる
  - 短所：導入時の手間が画面数に比例する。既存画面全てに手を入れる必要がある
- 折衷案として、`Button`/`IconButton`に「デフォルトON、propsでオプトアウト
  可能」の形で共通化しつつ、スイッチ切替・成功/失敗通知は個別追加する、
  という組み合わせが現実的に見える（ただし採用するかは開発者判断）

## 5. 懸念点・開発者に判断してほしい論点

1. **導入するかどうか自体**：そもそも触覚フィードバックを増やす価値がある
   機能かどうか（既存の入室通知振動だけで十分という判断もあり得る）
2. 導入する場合、**どの操作まで広げるか**（上記候補ポイントのうちどこまでか）
3. **強度**：`ImpactFeedbackStyle`には`Light`/`Medium`/`Heavy`等があるが、
   `docs/design-system.md`にハプティクスの強度方針の記載が無いため、採用する
   なら合わせてデザインシステム側への追記が必要
4. 設定画面の「入室通知時に振動する」のように、**ユーザー側でON/OFFできる
   設定にするか**、常時有効にするか（Issue #169は設定可能だが、通常の
   ボタンタップにまで同様の設定項目を用意するかは別論点）

## 6. 工数感

- Button/IconButtonへの共通追加のみであれば、既存コードへの影響は小さく
  （数行〜十数行程度）、小規模な作業で収まる見込み
- スイッチ切替・成功/失敗通知への展開は、対象画面数に応じて作業量が増える
