# ADR-0010: 認証方式をメールのマジックリンクから6桁コード入力に変更

## ステータス

[ADR-0009](0009-auth-email-magic-link.md)（メールのマジックリンク）を
置き換える。実機検証で見つかった問題への対応（2026-09-19）。

## 決定事項

- ユーザーのアプリ内本人確認は、Supabase Authの**メールアドレス＋
  6桁コード入力**（`supabase.auth.signInWithOtp({ email })`で送信、
  `supabase.auth.verifyOtp({ email, token, type: 'email' })`で検証）を使う。
  パスワードは引き続き不要
- ログインメールのテンプレート（`supabase/config.toml`の
  `[auth.email.template.magic_link]`、`supabase/templates/magic_link.html`）を
  カスタマイズし、**クリック可能なリンクを一切含めず**、`{{ .Token }}`
  （6桁コード）のみを平文で表示する
- ディープリンク（`oruca://login-callback`、`app.config.js`の`scheme`）は
  不要になったため削除する。あわせてSupabase Auth設定のRedirect URLsに
  登録していた`oruca://login-callback`も不要になる（登録を残していても
  実害は無いが、使われなくなる）
- `USERS.id`は引き続き`auth.uid()`と同じ値（変更なし）

## 理由

- ADR-0009のマジックリンク方式を実機で検証したところ、メールのリンクを
  ユーザーが実際にタップする前に「有効期限が切れています」というエラーに
  なる事象が複数回再現した
- 原因を切り分けたところ、以下が判明した：
  - ディープリンク自体（Supabase→`oruca://login-callback`→アプリ起動）は
    正常に機能していた
  - curlでの二重アクセスが原因ではないことも確認済み（1回のみのアクセスでも
    再現）
  - Gmail等のメールセキュリティ機能（フィッシング対策の自動リンクスキャン）
    が、ユーザーがタップする前にSupabaseの`/auth/v1/verify`エンドポイントへ
    自動的にアクセスし、そこで使い捨てトークンが消費されてしまっている
    可能性が高い（このURLがGoogleのリンクラッパー`google.com/url?q=...`
    経由だったこととも整合する）
- この問題は、クリックした瞬間にGETリクエストでトークンを消費する
  「リンク型」の認証フロー全般が抱える既知の課題であり、oruca固有の
  実装ミスではない
- 当初検討した「リンク先に確認ボタンを挟む」案は、根本解決にはならないと
  判明した。トークンが消費されるのはSupabaseの`/verify`エンドポイントに
  到達した時点であり、その後段に確認ページを挟んでも、メールに直接埋め込ま
  れた`/verify`リンク自体が事前スキャンされる問題は防げないため
- 6桁コードを画面に手入力させる方式であれば、自動スキャナーは「クリック」
  はしても「コードを読み取ってアプリに入力する」ことはできないため、
  この種の事前消費が原理的に起こらない

## 見送った選択肢

- **確認ページを挟む方式**：メールテンプレート自体をSupabaseの`/verify`
  ではなく自前の確認ページに向け、ボタンクリック時にのみ
  `supabase.auth.verifyOtp()`をブラウザ側JSで呼び、その結果（アクセス
  トークン等）をディープリンクでアプリに渡す、という設計であれば理論上
  実現できる。ただし認証フロー全体の作り替え（PKCEのcode交換から
  トークン直接受け渡しへの変更）が必要になり、実装コスト・検証コストが
  6桁コード方式より大きく上回ると判断した
- **メール＋パスワード**：ADR-0009から変わらず、パスワード管理コストを
  理由に見送り

## 実装メモ（引き継ぎ用）

- US-005（友達追加のOTP、`app/utils/otp.ts`・`otp_codes`テーブル）とは
  別の仕組み（Supabase Auth標準のメールOTP）であり、コードは共有しない。
  画面の文言（「oruca にログイン」）で紛らわしくないようにしている
- Supabase Studio（dev・prod両方）の**Redirect URLs**に登録していた
  `oruca://login-callback`は、今後不要（削除してもしなくても動作に影響はない）
- メールテンプレートの変更（`supabase/config.toml`）は`supabase config push`
  でリモートプロジェクトに反映する

## 振り返り（2026-10-02追記、Issue #33）

- **良かった点**：6桁コード方式に切り替えて以降、ADR-0009で起きていた
  「メールのリンクをタップする前にトークンが消費される」事故は一度も
  再発していない。ローカル開発（Mailpit）・実機検証のどちらでも安定して
  動作しており、方針転換の判断は正しかったと確認できた
- **ADR-0007→0009→0010という3段階の変遷自体**が、面接で「実機検証で
  見つかった問題にどう対応したか」を具体的に語れる材料になっている。
  特に「確認ページを挟む」という中間案を検討した上で、実装コストとの
  比較で見送った判断過程を記録できているのは良かった
- その後、Issue #151でオープングループ参加専用の`signInAnonymously`
  経路を追加した際、「通常ログインを置き換えない、別経路として追加する」
  という本ADRの設計（US-005のOTPとも混同しない）の考え方がそのまま
  踏襲できた。認証方式を1つに決め打ちせず、用途ごとに経路を分ける
  という方針は、後から機能を足す際にも破綻しなかった
- **今作り直すなら変える点**：特に無し。実機検証で問題が見つかってから
  方針転換する、というプロセス自体に無駄は感じていない
