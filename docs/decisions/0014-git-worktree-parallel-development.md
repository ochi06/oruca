# ADR-0014: git worktreeによる並行開発

## ステータス

実際には開発中盤（コミット840d059、`.claude/commands/new-us.md`）から
運用ルールとして機能していたが、ADRとして正式化していなかった。
Issue #33（技術選定の振り返り）で、振り返り作業時に後追いで文書化する。

## 決定事項

- 複数の実装作業（Issue／User Story）を並行して進める際、Issueごとに
  `git worktree add -b <branch> ../oruca-worktrees/<issue-id> main`で
  作業ディレクトリを分離する
- `app/node_modules`・`.env`・`.env.development`・`.env.production`
  （いずれも`.gitignore`対象）は、`oruca`（main）側の実体へ
  シンボリックリンクして共有する。これによりworktreeごとの
  `npm install`重複・環境変数ファイルの個別コピーを避ける
- Gitで追跡されているファイル（`docs/`・`CLAUDE.md`・`package.json`等）は
  絶対にシンボリックリンクにしない。ブランチごとに内容が独立しているのが
  正しい状態であり、共有すると他のworktreeの変更が意図せず混ざる事故になる
- worktreeは着手する直前にだけ作成し、事前にまとめて作らない
  （`.claude/commands/new-us.md`に手順化済み）
- 作業完了後（PRマージ後）は`git worktree remove`で都度削除する

## 理由

- 本プロジェクトは、AIとの並行セッション（複数のチャットが同時に別々の
  Issue／User Storyに着手する）という開発スタイルを取っている。単一の
  作業ディレクトリでブランチを切り替えると、別セッションの作業中ファイルが
  衝突する
- `git worktree`を使うことで、ブランチごとに独立したディレクトリを
  持ちつつ、同一の`.git`リポジトリ・コミット履歴を共有できる
- `node_modules`等の重い／環境依存のファイルをシンボリックリンクで共有する
  ことで、worktreeを作るたびに`npm install`をやり直すコスト（時間・
  ディスク容量）を避けられる

## 見送った選択肢

- **worktreeを使わず、作業ごとに別々のクローン（`git clone`）を作る**：
  `.git`ディレクトリが重複しディスクを圧迫する上、複数クローン間での
  コミット履歴の共有・参照がworktreeより煩雑になるため見送り
- **常時すべてのUser Story分のworktreeを事前に作っておく**：着手しない
  worktreeが放置され、`../oruca-worktrees/`配下が肥大化するリスクが
  高いため、着手直前にだけ作る運用にした

## 振り返り（2026-10-02追記、Issue #33）

- **良かった点**：AIとの並行セッションという開発スタイル特有の課題
  （同一ワーキングディレクトリの奪い合い）に対する実務的な解決策として、
  開発終盤まで一貫して機能した。並行して10件以上のIssueが同時進行する
  場面でも、ファイル衝突によるトラブルは発生しなかった
- **苦労した点**：
  - worktreeは「着手直前に作る」運用だったが、削除（`git worktree
    remove`）のタイミングが属人的になりやすく、PRマージ後の削除忘れが
    何度か発生した
  - 並行開発の副作用として、複数セッションが同時にマイグレーションファイルを
    生成すると、タイムスタンプ採番の衝突が実際に複数回発生した
    （`docs/decisions/0005-migration-workflow.md`の振り返り参照）。
    worktreeで作業ディレクトリは分離できても、「Supabaseマイグレーションの
    採番」のようなグローバルな名前空間の衝突までは防げない、という
    教訓を得た
  - `docs/`・`CLAUDE.md`のようなGit管理ファイルは意図的にシンボリックリンク
    にしていないため、並行して走る複数セッションがほぼ同時に同じドキュメント
    （特に`docs/must-manual-test-checklist.md`）を更新しようとすると、
    マージ時にコンフリクトやレースコンディション（片方の更新が
    もう片方の古い内容を上書きする）が発生することがあった
- **今作り直すなら変える点**：
  1. 本ADRのように、実際に機能している運用ルールは、文書化を後回しに
     せず早い段階で`docs/decisions/`に切り出すべきだった（振り返りの
     「まとめ」でも挙げた通り）
  2. 高頻度で複数セッションから更新されるドキュメント
     （`must-manual-test-checklist.md`等）は、「誰か1人が最後に
     まとめて更新する」役割分担を先に決めておくか、更新のたびに
     `git fetch`→`rebase`で最新化してから編集する運用を徹底すべきだった
