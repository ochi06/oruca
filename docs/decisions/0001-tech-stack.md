# ADR-0001: 技術スタックの選定

## 決定事項

- フロントエンド：React Native + Expo + TypeScript
- バックエンド／DB：Supabase（PostgreSQL）

## 理由

### React Native + Expo
- クロスプラットフォーム対応が必要（実機はAndroidのみ保有）
- 開発者はモバイル開発の立ち上げ経験がなく、環境構築の複雑さが
  最大のリスクだったため、環境構築が容易なExpoを採用
- 将来ネイティブ機能が必要になった場合も `expo prebuild` で
  ネイティブプロジェクトに移行できるため、後戻りできない選択ではない
- MVPはiOS/Android。将来的にiPad対応も見込むが、これは同じRN+Expo
  コードベースでレスポンシブ対応すればよく、追加の技術選定は不要
- 一方、Apple Watch（watchOS/SwiftUIが必要）とPC（デスクトップ向けの
  別ランタイムが必要）はReact Native + Expoの対象範囲外。対応する場合は
  本ADRとは別に技術選定が必要（現時点では未着手）

### TypeScript（JavaScriptではなく）
- AIと伴走しながら開発する方針のため、型があることでAIの実装ミスを
  エディタ上で早期検知できる
- 業界の標準になりつつあり、キャリア面でも学ぶ価値が高い

### Supabase（Firebaseではなく）
- 開発者はDB設計を自分の手で行いたいという意向があり、
  リレーショナルデータベース（PostgreSQL）の方が、ER図設計・正規化・
  SQLといった、面接で語れる土台の知識を学べる
- oruca自体のデータ構造（ユーザー・エリア・友達関係・グループの
  多対多関係）がリレーショナルデータベース向きである

## 見送った選択肢

- Firebase（Firestore）：NoSQLのため、DB設計の学習効果が薄いと判断
- Flutter：JavaScript/TypeScriptとの言語統一（フロント・バックエンド）の
  メリットを優先し見送り

## 振り返り（2026-10-02追記、Issue #33）

### React Native + Expo
- **良かった点**：環境構築の詰まりがほぼ無く、実装そのものに集中できた。
  `expo install`で依存パッケージのSDK互換性が自動解決されるため、
  「このバージョンの組み合わせでビルドが壊れる」という事故が最後まで
  起きなかった
- **苦労した点**：地図（`react-native-maps`）・QRコードスキャン
  （`expo-camera`）等のネイティブモジュールを使い始めた時点で、
  Expo Go（汎用クライアント）が使えなくなり、開発ビルド
  （`expo run:android`/`expo run:ios`）への切り替えが必要になった
  （ADR-0006）。これ自体は想定内だったが、「いつ・どのタイミングで
  Expo Goを卒業するか」という判断ポイントをADR時点で明記していれば、
  切り替え時の手戻りはもっと減らせた
- iPad対応・Apple Watch/PC対応は、当初の想定通り結局着手しなかった
  （スコープ外のまま。Must/Should完了を優先した結果、妥当な判断）

### TypeScript
- **良かった点**：選定理由（AI生成コードの型不整合をエディタで即検知）が
  そのまま効いた。特にSupabaseのテーブル行の型を手で定義する場面で、
  カラム名のtypoやnull許容の見落としをコンパイル時に拾えたのは大きい
- **今作り直すなら変える点**：`supabase gen types typescript`での型自動
  生成を使わず、各テーブルの型を`app/mocks/*.ts`や各ファイルで手書き・
  重複気味に定義してしまった。開発終盤で「`docs/schema.md`とコードの型が
  食い違う」というリスクに気づいたが、今から全面移行するには手戻りが
  大きく見送った。次に作るなら最初から自動生成に寄せたい

### Supabase（Firebaseではなく）
- **良かった点**：友達関係・グループ・エリアの多対多を中間テーブルで
  正規化する設計を自分の手で経験でき、狙い通りの学習効果があった。
  RLS（Row Level Security）を「アプリ側の認可チェックの代わりにDB側で
  強制する」設計に一本化できたのも、PostgreSQLベースだからこそ
- **苦労した点**：RLSポリシーの設計・検証は、CRUD経験だけでは足りず、
  `auth.uid()`・`security definer`関数・`RESTRICTIVE`ポリシーといった
  概念の理解が前提になり、何度か「書いたつもりのポリシーが実際には
  意図した経路を守っていなかった」というバグを本開発後半で複数発見した
  （例：友達関係のRLSを経路Aにだけ足して、`SECURITY DEFINER`のRPC経由の
  経路Bには反映されていなかった、等）。RLSは「書いて終わり」ではなく
  「実際のアプリの書き込み経路と突き合わせて検証して初めて正しさが
  わかる」という教訓を得た
- **今作り直すなら変える点**：現時点でもSupabase／PostgreSQLの選択自体に
  後悔は無い。ただし、RLSポリシーの「このテーブルのこの操作は、アプリの
  どの関数から、誰の権限で呼ばれるか」を一覧できるドキュメント
  （対応表）を設計初期から作っておけば、上記のような経路の見落としに
  もっと早く気づけたはず
