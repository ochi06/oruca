# ADR-0003: 環境構成とブランチ運用

## 決定事項

### 環境（Supabaseプロジェクトを3つ用意する）

| 環境 | 用途 |
|---|---|
| demo | 合宿デモ専用。作成済み。今後は凍結し、参照専用とする |
| dev | 日常の開発・動作確認用。汚れたデータが入ってもよい |
| prod | コンペ提出・審査員へのデモ用の安定版 |

### ブランチ運用（環境とは独立させる）

- ブランチは「コードの状態」、環境は「どのSupabaseプロジェクトに繋ぐか」であり、
  この2つは別軸として扱う
- Gitブランチ運用は既存方針のまま：`feature/us-XXX-name` → PR → `main`
  （`develop`のような長期ブランチは作らない。トランクベース開発）
- どの環境に繋ぐかは、ビルド時の環境変数（`.env.development` /
  `.env.production`、いずれも`.gitignore`対象）で切り替える
- EAS Buildを使う場合は`eas.json`に`development`・`production`の
  ビルドプロファイルを用意し、それぞれ異なる環境変数を注入する

## 理由

- モバイルアプリはWebサービスと異なり、「ブランチ＝デプロイ先」という
  CI/CDの考え方をそのまま当てはめにくい（ビルドしたバイナリを配って
  試してもらう形式のため）
- ブランチを環境の数だけ増やすと、ブランチ運用が複雑になり、
  一人開発のシンプルさが失われる
- 環境変数による切り替えの方が、実務でも一般的でシンプル

## 見送った選択肢

- `develop`ブランチを作り、`main`=prod、`develop`=devとする
  Git Flow的な運用：一人開発では管理コストが見合わないため見送り

## 振り返り（2026-10-02追記、Issue #33）

- **良かった点**：トランクベース開発（`main`のみ）は最後まで破綻しなかった。
  User Story／Issue単位でブランチを切ってPRを出す運用は、一人開発でも
  「面接で語れるGit運用経験」として機能し、`main`をシンプルに保てた
- **想定通りにいかなかった点**：`demo`環境は、合宿デモ用モック（`demo/`）
  自体を作成途中で中止したため、結局一度も実質的に使われなかった
  （CLAUDE.md「現在のステータス」参照）。「3環境を先に決めておく」という
  判断自体は悪くなかったが、`demo`環境を作った時点ではまだ本開発の方針
  転換前で、環境設計が先走った形になった
- EAS Buildの実際のプロファイル名は、本ADRが想定していた
  `development`/`production`の2本ではなく、ブース配布検証用に
  `preview`（internal distribution、APK直接配布）を先に用意する形に
  なった（`eas.json`、Issue #169関連）。「環境」（どのSupabaseに繋ぐか）と
  「ビルドプロファイル」（配布形態）は、本ADRで述べた通り別軸ではあるが、
  本ADR本文はプロファイル名を決め打ちで書いており、実態と少しずれている
- **今作り直すなら変える点**：環境の数（demo/dev/prod）を先に決め打ちせず、
  「今何が必要か」が明確になった時点で1つずつ増やす方が、作って使わない
  環境（`demo`）を防げたはず
