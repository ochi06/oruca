# ADR-0013: 本番DBバックアップ・障害対応方針

## 背景・目的

コンペ提出・審査員デモ用の安定版であるprod環境（[ADR-0003](0003-environments-and-branching.md)）が
壊れた場合の復旧手段を事前に決めておく（Issue #26）。oruca（demo/dev/prod）は
いずれも個人開発・コンペ提出目的のため、**費用をかけない前提**で検討する。

## 決定事項

### 採用：手動バックアップ（`supabase db dump`）＋マイグレーション再適用による復旧

- **自動バックアップ・PITR（Point-in-Time Recovery）は導入しない**。
  Supabaseの自動デイリーバックアップはPro以上のプランでのみ提供され
  （Free：バックアップ無し、Pro：7日分のデイリーバックアップ、
  Team：14日分）、PITRはPro/Team上でさらに追加課金（7日分の保持で
  月額$100〜、14日で$200〜、28日で$400〜）が必要。費用をかけない方針の
  個人開発では過剰
- 代わりに、**開発者が手動で`supabase db dump`を実行し、ダンプファイルを
  手元（またはプライベートなストレージ）に保管する**運用にする
- 障害発生時は、Gitの`supabase/migrations/`（スキーマの実行履歴、
  [ADR-0005](0005-migration-workflow.md)）から新しいSupabaseプロジェクトに
  スキーマを再構築し、直近の手動ダンプからデータを復元する

### 手動バックアップの実行方法

```bash
# スキーマ＋データ両方（実行前に --dry-run で内容を確認してもよい）
supabase db dump --linked -f backups/prod_$(date +%Y%m%d).sql

# 特定のタイミング（例：コンペ提出直前）には必ず取得する
```

- ダンプファイルは`.gitignore`対象のローカルディレクトリ（例：`backups/`）に
  置き、リポジトリにはコミットしない（個人情報・位置情報を含むため、
  [ADR-0011](0011-secrets-management.md)の秘匿情報の扱いに準じる）
- 取得頻度は「決まったタイミングで手動実行」とし、常時スケジュール化は
  しない（下記「見送った選択肢」参照）。最低限、**コンペ提出直前には
  必ず取得する**（`docs/security-review-checklist.md`に追記）

### 障害発生時の復旧手順

1. 新しいSupabaseプロジェクト（またはprodプロジェクトの復旧機能）を用意する
2. `supabase link --project-ref <新プロジェクトのref>` → `supabase db push`で、
   Gitの`supabase/migrations/`からスキーマを再構築する（[ADR-0005](0005-migration-workflow.md)の通常の反映フロー）
3. 直近の手動ダンプ（コンペ提出直前のものを優先）から`psql`等でデータを復元する
   ```bash
   psql "<新プロジェクトの接続文字列>" -f backups/prod_YYYYMMDD.sql
   ```
4. `.env.production`の接続情報（URL・anon key等）を新プロジェクトのものに
   更新し、アプリ（EASビルド等）から新しいプロジェクトに向くようにする
5. 主要User Story（US-018エリア登録→US-004ジオフェンス→US-001在席表示等）が
   動作することをスモークテストで確認する

**この手順では、直近の手動ダンプ取得時点までのデータ（それ以降の入退室ログ等）は
失われる。** コンペ提出目的では許容範囲と判断する（下記「見送った選択肢」参照）。

### 関連する運用リスク：Freeプランの7日間無操作による自動一時停止

バックアップとは別の論点だが、障害対応・可用性に関わるため併記する。
Supabase Freeプランのプロジェクトは、**7日間データベースへのアクセスが
無いと自動的に一時停止（pause）される**（データ自体は保持されるが、
ダッシュボードから手動で再開するまでアプリから利用できなくなる）。
コンペ提出〜審査員デモまでの間、prod環境へのアクセスが疎になる期間が
できると、デモ直前に気づかず一時停止していた、という事故が起こり得る。

- 対応方針：審査員デモが近づいたら、開発者が事前にSupabaseダッシュボードで
  prodプロジェクトの状態を確認し、一時停止していれば再開しておく
  （デモ直前チェックリストに追記）
- 継続的な自動ping（GitHub Actions等での定期ヘルスチェック）による予防は、
  個人開発の運用コストに見合わないため見送る。手動確認で十分とする

## 理由

- PITR・Proプランへの常時アップグレードは、月額$25〜（Pro）＋PITR分
  $100〜の継続課金が発生し、コンペ提出目的の個人開発には見合わない
- 障害発生の許容範囲（直近の手動バックアップ時点まで巻き戻ってよい）を
  考えると、PITRのような「任意の秒単位まで戻せる」機能は過剰
- マイグレーションファイルは既にGit管理されている（ADR-0005）ため、
  スキーマの再構築自体には追加コストがかからない。失われうるのは
  「スキーマ」ではなく「データ」のみであり、手動ダンプで十分カバーできる

## 見送った選択肢

- **PITRの導入**：月額$100〜の継続課金はコンペ提出目的の個人開発には
  見合わない
- **Proプランへの常時アップグレード**：バックアップ目的だけでなら手動dumpで
  代替可能なため見送り。ただし他の理由（コンピュートリソース等）でPro化
  する場合は、その際に自動デイリーバックアップも副次的に得られる、
  という位置づけで良い
- **定期スケジュールでの自動バックアップ**（GitHub Actions等で`supabase db
  dump`を定期実行しアーティファクトとして保存する等）：個人開発・低頻度の
  更新ペースでは、決まったタイミング（コンペ提出直前等）での手動実行で
  十分と判断。将来、更新頻度が上がった場合は再検討する
- **Freeプラン一時停止への自動pingによる予防**：継続的な運用コストに見合わないため、
  デモ直前の手動確認で代替する
