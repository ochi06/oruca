# oruca

**エリア限定・関係限定の在席可視化アプリ**

大学やオフィスなど、あらかじめ登録した特定のエリアに入った時だけ位置情報を検知し、
それ以外の場所・時間のデータは一切保存・送信しない。登録エリアに友達・グループが
今いるかどうかだけを、プライバシーを守りながらリアルタイムに可視化する。

## 解決したい課題

リモートワークと出社を自由に選べる働き方や、決まった集合スケジュールのない
サークル・学祭実行委員会のような課外活動では、「行ったのに誰もいなかった」
「行かなかった日に限って人が大勢いた」「行けば話したい人に会えたかもしれない」
という判断ミスが起きがちである。この"行くかどうか"の判断は、単一の組織や
シーンに限らず、フレキシブルな共同作業活動全般で共通して発生する課題であり、
出社・登校するモチベーションや、偶発的な対話から生まれる相談・アイデア交換の
機会に直結する。

既存の位置情報共有アプリ（whoo、Life360など）の多くは常時トラッキングを
前提としており、心理的な抵抗感を抱くユーザーも多い。oruca は、**エリア限定**
（登録エリアの外では位置情報を一切扱わない）・**関係限定**（紐づけた友達・
グループにしか在席情報を見せない）・**プライバシー・バイ・デフォルト**
（エリア外のデータは生成・保存すらしない）の3原則で、この課題にプライバシー
重視の形で応える。詳細な要件・ユーザーストーリーは [`docs/oruca_PRD.md`](docs/oruca_PRD.md) を参照。

## 実装済みの主な機能

| 機能 | 概要 |
|---|---|
| エリア登録・管理 | 地図上でピン＋半径を指定してエリアを登録。既存の公開エリアを検索して監視対象に追加することも可能（US-018） |
| ジオフェンス判定による在席検知 | 登録エリアへの入退室を検知し、在席ログ（PRESENCE_LOGS）を記録（US-004） |
| リアルタイム在席人数・友達の在席確認 | マップ上のエリアタップで、在席者数と（名前表示の合意がある）友達の在席状況を表示（US-001, 002） |
| OTPによる友達追加 | 対面での6桁コード／QRコードの相互入力でのみ友達関係が成立し、又聞き・なりすましによる追加を防止（US-005） |
| グループ機能 | オープン/クローズの2種別。オープンは招待コード/QRで承認不要・即時参加、クローズは招待制。招待の承諾/却下・強制退会・自主退会・管理者譲渡に対応（US-006, 010, 019、Issue #116, #117, #148, #202） |
| 友達ごとの通知・公開設定 | 入室通知ON/OFF・ミュート・共在時は常に通知（オフにはできない）・会いたい人指定（共在していなくても通知）・会いたい人への入室通知の全体許可（US-007, 016, 017、Issue #270で通知ロジックを統合・整理） |
| 友達のブロック・削除 | 特定の相手に在席・滞在予定・グループ内在席を見せなくする一方向ブロック、友達関係そのものを双方向に解消する削除（物理削除、再追加にはOTPが必要）をそれぞれ一覧・詳細画面の「…」メニューから実行可能（US-008、Issue #121, #271, #276） |
| 匿名モード | ワンタップで一時的に在席・名前を非公開にする（US-013） |
| 滞在予定の共有 | エリアごとの基本滞在予定・当日の上書き予定を、承認済みの友達にのみ公開（US-011） |
| プッシュ通知配信 | 入室イベントをDatabase Webhook経由でEdge Functionが判定し、Expo Push経由でOS通知として配信（Issue #131） |
| 入室時のまとめ通知 | 会いたい人の入室を個別に通知せず、「今会える人一覧」として通知ボックスに集約（US-021、Issue #163） |

いずれの機能もRow Level Security（RLS）によってDBレベルでアクセス制御されており、
クライアント側の実装ミスだけでは他人のデータへアクセスできない設計になっている
（詳細は[`docs/schema.md`](docs/schema.md)「設計上の重要な原則」を参照）。

### 既知の制約・今後の課題

開発の透明性のため、未検証・未対応の点も明記する。

- **バックグラウンド位置検知は未移行**：現状は`watchPositionAsync`（フォアグラウンド
  中心の継続取得）で動作しており、OS標準のジオフェンスAPI
  （`startGeofencingAsync`）への切り替えは未着手。アプリを閉じている間の
  検知精度は本来の設計目標を満たしていない（詳細は[`docs/architecture.md`](docs/architecture.md)参照）
- **iOS実機検証が未実施**：開発者がiOS実機を保有していないため、シミュレータでの
  確認のみ。TestFlight経由での第三者検証を準備中
- **通知Edge Functionのdev環境デプロイが未完了**：`arrival_summary`
  （入室時のまとめ通知）・`group_invite`（グループ招待通知）を含む通知生成
  ロジック自体はEdge Function側に実装済みだが、Database Webhookの設定は
  デプロイ済みEdge Functionを前提とするため（`docs/supabase-dashboard-setup-notes.md`
  参照）、dev環境への反映・動作確認はまだ完了していない

## アーキテクチャ・技術スタック

| レイヤー | 技術 | 選定理由 |
|---|---|---|
| フロントエンド | React Native + Expo + TypeScript | クロスプラットフォーム対応、環境構築の容易さ、型による実装ミスの早期検知 |
| バックエンド／DB | Supabase（PostgreSQL） | DB設計を自分の手で行いたいという学習目的に合致。RLSでアクセス制御をDBレベルに寄せられる |
| 認証 | Supabase Auth（メール＋6桁コード） | マジックリンク方式で実機検証中に見つかった、メールセキュリティ機能によるトークン事前消費の問題を回避（[ADR-0010](docs/decisions/0010-auth-email-otp-code.md)） |
| 地図 | react-native-maps | [ADR-0006](docs/decisions/0006-map-library.md) |
| 状態管理 | Zustand | 画面ごとのローカル状態・Supabaseから取得したデータのキャッシュに利用 |
| 通知配信 | Expo Notifications + Supabase Edge Functions | クライアントを信用せず、入室通知の判定・送信をすべてservice role側（Edge Function）で実施 |

システム構成図・コンポーネント間のデータフロー、画面構成、エンティティの
状態遷移などの詳細設計は[`docs/architecture.md`](docs/architecture.md)、
ER図・テーブル定義・RLSの設計原則は[`docs/schema.md`](docs/schema.md)を参照。
技術選定の経緯は[`docs/decisions/`](docs/decisions/)（ADR形式）にまとめている。

## 開発で工夫した点

- **プライバシー・バイ・デフォルトをDB設計レベルで徹底**：友達への在席・滞在予定の
  公開は、クライアント側のフィルタではなく、`FRIEND_AREA_LINKS.status = 'approved'`
  を条件としたRLSポリシーでDBレベルに強制している。アプリのバグや悪意ある
  クライアント改造があっても、未承認の相手に情報が漏れない設計になっている
- **RLSをまたぐ処理はSECURITY DEFINER関数で最小権限に封じ込める**：OTPコードの
  検証とFRIENDSHIPS作成は、本人以外の行を操作する必要があるためRLSの素朴な
  適用だけでは実現できない。これをクライアントに権限を渡す形で解決せず、
  Postgres の SECURITY DEFINER 関数（`redeem_friend_otp`）に検証ロジックを
  閉じ込め、行ロック（`FOR UPDATE`）と一意制約（`otp_codes`の部分unique
  index、`friendships`のunique制約）を組み合わせることで、同時多重実行時の
  不整合（別人のコードの誤認識、重複した友達関係の作成）も防いでいる
- **AIとの協働を前提にした開発プロセス自体の設計**：要件定義・DB設計などの
  上流工程は開発者が担い、実装はAI（Claude Code）と役割分担しながら、
  User Story単位でのブランチ運用・PRレビュー・CIによる型チェック/テスト/lintの
  自動化を徹底した。協働方針そのものを`CLAUDE.md`・`docs/ai-collaboration-plan.md`
  として明文化し、プロジェクトの進行とともに継続的に見直している

## セットアップ

本番アプリ（`app/`）のセットアップ・実行方法（Android/iOSエミュレータ・実機、
既知のトラブルと対処を含む）は [`app/README.md`](app/README.md) を参照。

```bash
cd app
npm install
npx expo run:android   # または npx expo run:ios
```

（`react-native-maps`等のネイティブモジュールを使用しているため、Expo Go
ではなくdevビルドでの実行が必要。詳細は`app/README.md`参照）

## 開発の進め方

1. 設計・方針は必ず `docs/` を参照してから着手する
2. AIと実装する際の役割分担は `docs/ai-collaboration-plan.md`・`CLAUDE.md` を確認する
3. User Story・Issue単位でブランチを切り、PR上でCI（lint・型チェック・テスト）を通してからマージする
